# Database Schema — Dialysis Vascular Access Registry

| | |
|---|---|
| **Status** | Approved schema design, v1.0 (2026-07-09) |
| **Engine** | PostgreSQL 16, accessed exclusively through Django ORM |
| **Companion** | `docs/PRODUCT_SPEC.md` (v1.0) |
| **Relation to code** | Tables marked **[implemented]** exist in migrations today. Tables marked **[new]** and column notes marked **Δ** are the delta to build. §14 summarizes the full delta. |

Conventions used below:

- Physical table names follow Django's `app_model` convention (e.g. `patients_patient`); the headings use the logical name.
- Every table has `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` unless stated otherwise; PK is omitted from the field lists.
- Clinical tables carry `created_at timestamptz NOT NULL` and `updated_at timestamptz NOT NULL` (from `TimeStampedModel`); omitted from field lists.
- **✱** = `NOT NULL`. Text enums are `varchar` with app-level choices **plus** a DB `CHECK` constraint (Django `CheckConstraint`) on clinical outcome fields.
- "Void" pattern: clinical rows are never physically deleted by users. **Δ** add `is_voided boolean NOT NULL DEFAULT false` + `void_reason varchar(255)` to every clinical event table (marked "voidable" below). All queries filter `is_voided = false` by default.

## 1. Entity-relationship overview

```
                                   users ──────────────┐
                                     │ (actor FKs)     │
 dialysis_center ◄─── patient ───────────────────────┐ │
        ▲              │  │ │                        │ │
        │              │  │ └── patient_status_event │ │
        │              │  └──── clinical_note        │ │
        │              │                             │ │
        │              ├── vessel_mapping ◄──┐       │ │
        │              ├── access_plan ──────┘       │ │
        │              │      │ (based_on_mapping)   │ │
        │              ▼      ▼ (plan)               │ │
        │        vascular_access  ◄──────────────────┘ │
        │              │ 1:1                           │
        │              ├── catheter_detail             │
        │              ├── maturation_assessment (1:N) │
        │              ├── access_procedure (1:N) ──── procedure_device ──► device
        │              │        ▲                      │
        │              │        │ (treats)             │
        │              ├── access_complication (1:N)   │
        │              │        ├── infection_detail        (1:1, infections only)
        │              │        └── thrombosis_dysfn_detail (1:1, thrombosis/dysfunction)
        │              └── dialysis_session_log (1:N) ◄─ recorded at dialysis_center
        │
        ├── follow_up_task (patient, optional access/complication)
        ├── alert          (patient, optional access/complication/session)
        └── attachment     (patient + generic target)

 audit_log, export_log, registry_setting, role_permission, patient_share — cross-cutting
```

Reading the model:

- **`patient` is the root.** Every clinical row reaches a patient in ≤ 2 joins. Identifiers (name, national ID, phone, address, exact DOB) exist **only** on `patient`.
- **`vascular_access` is the clinical unit of outcome analysis** ("access episode"): one row per fistula, graft or catheter. Its milestone dates anchor every KDOQI endpoint. A patient has many access episodes over a lifetime; episodes never merge — a new access after abandonment is a new row.
- **Events hang off the access**: `access_procedure` (index creation + every reintervention), `access_complication` (adverse events), `maturation_assessment` (structured follow-up), `dialysis_session_log` (functionality evidence).
- **Type-specific detail is vertically partitioned** into 1:1 extension tables (`catheter_detail`, `infection_detail`, `thrombosis_dysfunction_detail`) instead of widening the parent with mostly-NULL columns. The parent stays queryable for aggregate analytics; the extension carries specialist fields.
- **People**: one `users` table for all humans who act in the system, including nephrologists (role = `nephrologist`). Referring nephrologists who never log in are user rows with an unusable password — one identity table, no duplicate "clinician" entity. Dialysis centers are an organization table referenced by patients, users (nurses), and session logs.
- **Workflow tables** (`follow_up_task`, `alert`) reference clinical rows but are operational, not research data.
- **`audit_log`** is append-only and references rows polymorphically (`model_label` + `object_pk`) so history survives even voiding.

## 12. Cross-cutting design notes

### 12.1 Calculated values — never stored

| Value | Derivation |
|---|---|
| Patient age | `date_of_birth` vs reference date (age at creation, at export…) |
| Days to maturation | `maturation_confirmed_on − created_on` |
| Days to first (successful) cannulation | milestone dates − `created_on` |
| **Primary patency interval** | `created_on` → earliest of: first post-creation `access_procedure`, first `thrombosis` complication, abandonment; censored at death/transplant/transfer (from `patient_status_event`) or study end |
| **Assisted primary patency** | `created_on` → first thrombosis; same censoring |
| **Secondary patency** | `created_on` → `abandoned_on`; same censoring |
| Early thrombosis flag | thrombosis `onset_date − created_on ≤ 30` |
| Catheter dwell days ("catheter clock") | `removed_on` (or today) − `created_on` for catheter episodes |
| Catheter-days denominators (CRBSI per 1000) | sum of dwell intervals over the analysis window |
| Catheter-only patient flag | on HD with no fistula/graft in status `maturing/ready/in_use` |
| Successful-session count (A15, W10 trigger) | count over `dialysis_session_log` |
| All alert conditions A1–A15 | queries over the tables above; `alert` rows persist *instances*, never the logic inputs |
| Task overdue flag | `due_date < today AND status='open'` |
| Dashboard aggregates | computed per request (MVP) / materialized views (advanced, refreshed nightly) |

Two deliberate exceptions (documented denormalizations with a single writer): `patient.current_status/current_status_date` (maintained from status events) and `vascular_access.status` (maintained by workflow transitions). Both are recomputable from event history.

### 12.2 Data privacy

1. **Identifier isolation.** Direct identifiers (names, national_id, phone, address, exact DOB) live only in `patient`. Everything else joins by surrogate FK; `registry_code` is the stable pseudonym.
2. **Researcher column firewall.** The researcher role never receives identifier columns — enforced in the export/dashboard query layer (explicit column lists, never `SELECT *`), not by trusting the UI. Exports carry `registry_code` + birth **year** only.
3. **Small-cell risk.** Georgian regions + rare access types can re-identify; exports bucket region to broader zones when a cohort cell < 5 (advanced; documented limitation in MVP).
4. **Audit everything.** Clinical writes → `audit_log` (with per-field diffs); exports → `export_log`. Audit browser restricted to surgeon/coordinator, since diffs contain identifiers.
5. **No physical deletes.** Voiding keeps rows; the DB app role has no DELETE grant on clinical tables and no UPDATE/DELETE grant on `audit_log` in production.
6. **Transport/storage.** TLS-only; PostgreSQL encrypted volumes; encrypted off-site backups; attachments served through authenticated views (no direct file URLs).
7. **Legal.** Processing register + patient information per Georgian Law on Personal Data Protection; registry consent recorded (attachment type `patient` consent scan, advanced); retention: clinical data retained per medical-records law, audit ≥ the same period.
8. **Accounts.** Per-person accounts only (no shared center logins), 8-hour session expiry (configured), unusable passwords for non-login clinician records.

## 13. Integrity rules enforced outside pure SQL

Postgres can't cheaply express these; they are enforced in the Django layer (model `clean()`/service functions) and covered by tests:

1. `catheter_detail` only on catheter-type accesses; `infection_detail`/`thrombosis_dysfunction_detail` only on matching complication types.
2. Access status transitions follow the §4 state machines (e.g. a catheter never enters `maturing`).
3. Milestone dates ≥ `created_on` across tables (same-table cases are DB CHECKs; cross-table cases app-level).
4. `patient.current_status` recomputation on status-event write/void (single code path, already implemented).
5. Role/scope write rules (§2 matrix) — application permission layer.
6. Only one non-voided creation procedure per access (DB partial unique ignores voided rows: condition becomes `procedure_type='creation' AND NOT is_voided`).
